# MerkeMail – Setup & Testing Guide

MerkeMail is a **Python (FastAPI) backend + static HTML/JS frontend**. There is nothing to compile:
"building" = creating a virtualenv and installing dependencies. The backend serves the UI itself.

```
proyecto/
├── run.py                 # Web mode: starts uvicorn + opens your browser (port 8000)
├── backend/               # FastAPI app (backend.main:app), SQLite, IMAP/SMTP, Google APIs, Gemini
├── frontend/              # index.html + js/ + css/ (served at / and /static)
├── desktop/               # Optional native window (PyQt6) + tray icon (port 6524)
├── tests/smoke_test.py    # Automated API smoke test (isolated, offline)
└── data/                  # Created at runtime: merkemail.db, .secret.key, logs  (git-ignored)
```

## 1. Requirements

| Need | Notes |
|---|---|
| Python **3.11+** (tested with 3.12) | `python3 --version` |
| Linux / macOS (Windows via WSL) | Desktop mode and `launcher.sh` are Linux-oriented |
| Internet (optional) | Tailwind is served locally (`frontend/js/vendor/tailwindcss-3.4.17.js`), so the UI works offline. Only the Inter font (Google Fonts) and sender avatars need Internet, and both fall back gracefully. |

## 2. Quick start (one command, Linux/macOS)

```bash
./setup.sh            # install + automated test + start the web app
./setup.sh install    # only install (.venv + requirements)
./setup.sh test       # only run the automated smoke test
./setup.sh run        # only start the web app (http://127.0.0.1:8000)
./setup.sh desktop    # install PyQt6 and start the desktop version
./setup.sh reset      # delete data/ -> next start loads demo data again
```

## 2b. Manual install

```bash
cd proyecto
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
# Optional, only for the native desktop window:
pip install -r requirements-desktop.txt
```

`requirements.txt` had 4 pins to versions that don't exist on PyPI; they were corrected
(certifi 2026.10.18, fastapi 0.162.7, google-antigravity 0.1.22, soupsieve 4.1).

## 3. Run

**Web mode (recommended for testing)**
```bash
python run.py                 # http://127.0.0.1:8000, opens browser automatically
PORT=8080 python run.py       # other port
# or without opening a browser:
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --reload
```
API docs (Swagger, auto-generated by FastAPI): **http://127.0.0.1:8000/docs**

**Desktop mode (native frameless window + tray)**
```bash
./desktop/launcher.sh         # starts backend on port 6524 and opens a PyQt6 window
```
Logs go to `data/backend_desktop.log`.

## 4. First launch = demo data

On an empty database the app seeds **2 fake accounts** (`usuario@gmail.com`, `contacto@proton.me`),
5 demo emails, labels and 2 signatures, so you can explore the UI immediately.
The fake accounts can't sync (you'll see harmless sync errors in the console).
**Delete them in "Cuentas conectadas" before adding your real accounts.**

### 4b. More realistic test mail (several days of traffic)

The 5 demo emails are not enough to test pagination, folders, filters or unread counters.
`tests/generate_test_emails.py` adds ~2 weeks of fictitious mail **to every active account in the DB**
(it never sends anything or touches the 5 original emails):

```bash
./setup.sh seed --add-accounts --reset   # create the 2 extra test accounts (server must be running) + generate mail
./setup.sh seed                  # or: .venv/bin/python tests/generate_test_emails.py
./setup.sh seed --days 7         # shorter window (1-90 days, default 14, ending "now")
./setup.sh seed --reset          # replace previously generated mail (e.g. next day, so it looks fresh again)
./setup.sh seed --purge          # remove all generated mail (and the contacts derived only from it)
./setup.sh seed --dry-run        # print what would be generated, write nothing
./setup.sh seed --tz America/Mexico_City   # office hours in that time zone (default: system TZ)
```

The server can stay running; reload the browser afterwards (contacts are refreshed via `POST /api/contacts/sync`).

`--add-accounts` creates, through the app's own API (same as the "Cuentas conectadas" form), two extra accounts
with a default signature each. It skips addresses that already exist:

./setup.sh seed-calendar --reset         # regenerate (also after `./setup.sh seed --reset`, to re-link emails)
./setup.sh seed-calendar --purge         # remove only the generated calendars/events/tasks

./setup.sh seed-calendar --months-back 3 --months-ahead 1

Reset everything at any time (stop the server first):
```bash
rm -rf data/        # removes DB, encryption key and logs -> next start = fresh demo
```
⚠️ Deleting `data/.secret.key` alone makes stored passwords/tokens unreadable.

## 5. Automated smoke test

```bash
python tests/smoke_test.py
```
It copies the project to a temp directory, starts the backend on a free port with a fresh DB
(your real `data/` is never touched), and checks ~37 operations: static files, settings, accounts
(including that passwords/OAuth tokens are **not** exposed), emails (list/detail/search/star/read),
labels, signatures, contacts, events, tasks, controlled AI errors without API key, desktop state.
Exit code 0 = all OK. Use `--keep` to keep the temp dir + server log.

## 7. Setting up Google OAuth (Gmail + Calendar + Tasks)

1. https://console.cloud.google.com → create a project.
2. **APIs & Services → Library**: enable **Gmail API**, **Google Calendar API**, **Google Tasks API**.
3. **OAuth consent screen**: type *External*, status *Testing*, add **your Gmail as Test user**
   (the `https://mail.google.com/` scope is restricted; only test users can authorize).
4. **Credentials → Create OAuth client ID → Web application**, Authorized redirect URIs – add all you'll use:
   - `http://127.0.0.1:8000/api/auth/google/callback` (web mode)
   - `http://localhost:8000/api/auth/google/callback` (if you open via localhost)
   - `http://127.0.0.1:6524/api/auth/google/callback` (desktop mode)
5. In MerkeMail: Accounts → "Conectar con Google (OAuth 2.0)" → paste Client ID + Client Secret → authorize in the Google window.
   (Or export `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` before starting.)

The redirect URI must match **exactly** the host/port in your browser address bar.

## 8. Known issues found during testing

- **Tailwind runs in the browser**: the local file is the Tailwind *Play CDN* runtime (v3.4.17), which generates the CSS
  on each page load and logs a console warning ("should not be used in production"). It works offline; for a
  lighter production build, precompile with the Tailwind CLI (`npx tailwindcss@3 -o frontend/css/tailwind.css --minify`).
- **Demo calendar events don't appear**: the seed inserts 2 events into calendars 1/2, but the calendar
  service only shows Google calendars linked to an account and purges non-Google ones.
- On a brand-new DB, events created in the first seconds (before the background calendar init runs) can
  land in an orphan calendar and be invisible.
- `POST /api/desktop/reinstall` expects `scripts/install_desktop.sh`, which is not in the repo (`/scripts/` is git-ignored).
- The demo Gmail account is configured against the real `imap.gmail.com`; the background sync will attempt to
  log in with a fake password every 5 minutes until you delete it.
- `PyQt6` is used by `desktop/app_window.py` but wasn't listed in requirements → now in `requirements-desktop.txt`.
- Both demo accounts are created with the same color (`#ef4444`, the column default), so in "Todas las cuentas"
  you can't tell Gmail and Proton mail apart by the color marker. Change one in "Cuentas conectadas" to test that feature.
- Demo email #3 ("Reunión de Planificación…") has `has_attachments=1` but no row in `attachments`: the UI shows the
  clip icon but no files, and each time it is opened the backend tries the Gmail API and logs
  "Aviso extrayendo adjuntos bajo demanda… credentials do not contain the necessary fields".
- The "Importantes" view is always empty: it filters `folder = 'IMPORTANT'`, but no sync path ever stores that folder
  (Gmail's IMPORTANT is a label, not a folder).
- Deleting an account (`DELETE /api/accounts/{id}`) leaves its emails in the DB (SQLite foreign keys are not
  enabled), and they keep appearing in "Todas las cuentas" without account name/color. For generated mail,
  run `./setup.sh seed --reset` (or `--purge`) after deleting an account to clean them up.
- **Calendar – "Próximos eventos"** shows the *oldest* 5 events in the DB, not the upcoming ones
  (`renderUpcomingList` takes `events.slice(0, 5)` without filtering by date). With the calendar test data it lists
  events from 2 months ago.
- **Calendar – week view columns are misaligned** when a week has events: each hour row is its own flex row and the
  day cells (`flex-1`) have no `min-w-0`, so cells with longer titles get wider. Adding `min-w-0` to the slot `div`
  in `renderWeekView` aligns them (verified in the browser).
- **Calendar – week view only draws 07:00–21:59** (day view 06:00–23:59): events outside that range (06:30 runs,
  22:00 deploys, 01:00 maintenance in the test data) are only visible in the month view.
- **Calendar – Google dates shift one day west of UTC**: the Google sync stores all-day events as `YYYY-MM-DD` and task
  due dates as `YYYY-MM-DDT00:00:00.000Z`; the event detail parses them as UTC, so in Mexico (UTC-6) an all-day event
  on the 20th shows "Jueves 19" and a task due on the 20th shows "19 … 06:00 PM" (the month grid is right). The test
  data uses the same naive local format as events created in the UI, so it is not affected.
- **Fixed – IMAP sync (Proton Bridge, custom servers, Gmail with app password):**
  1. Emails archived / moved to Spam or Papelera came back to Recibidos as duplicates on the next sync
     (existing messages were only looked up in the same local folder). Each email now stores the server mailbox it
     came from (`emails.source_folder`) and is recognised by mailbox + UID wherever the user moved it.
  2. Message *sequence numbers* were stored as `uid`; after a deletion on the server new mail was skipped.
     Now real IMAP UIDs are used (`UID SEARCH` / `UID FETCH`).
  3. Server mailboxes were stored with their server name (`Sent`, `Junk`, `[Gmail]/Enviados`…), so they never
     appeared in Enviados / Spam / Papelera. They are now mapped to `SENT`/`DRAFT`/`SPAM`/`TRASH`/`ARCHIVE`
     (SPECIAL-USE flags or common English/Spanish names); virtual mailboxes (`\All`, `\Flagged`) are skipped.
  Rows written by older versions are migrated automatically on the next sync (matched by sender+subject+date,
  keeping the user's folder/read/star state and removing the duplicates the bug created). The table constraint
  `UNIQUE(account_id, folder, uid)` was replaced by a unique index that includes `source_folder` (same rule for
  Gmail API rows).
- **IMAP – Archivar / Spam / Papelera are reflected on the server.** The local folder is the user's decision and
  `source_folder` is where the message really is on the server; when they differ the move is pushed in the
  background right after the action (buttons, "No es spam", viewer delete, Elio agent) and retried at the start
  of every sync if the server was unreachable. Target mailboxes are found by SPECIAL-USE flag or name and created
  if missing (Gmail IMAP: archive = `[Gmail]/All Mail`; restoring from it only *copies* back to INBOX).
  Uses `UID MOVE`, or `COPY` + `\Deleted` + `UID EXPUNGE` (without UIDPLUS no global EXPUNGE is issued; the
  original stays flagged `\Deleted` and sync ignores it). "Eliminar definitivamente" (from Papelera) removes the
  email from MerkeMail but only moves it to the server's Trash – it is never destroyed on the server.
  The viewer's "Mover a papelera" now really moves to Papelera (before it deleted the row); from Papelera it asks
  "¿Eliminar definitivamente?". Read/starred state is still not pushed to IMAP servers.
- Demo emails use numeric UIDs (101–104, 201). If real credentials are later set on those same demo accounts,
  real INBOX messages with those UIDs would be skipped by the IMAP sync (it skips UIDs already in the DB).
